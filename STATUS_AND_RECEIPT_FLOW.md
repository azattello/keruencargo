# Схема работы статусов филиала, клиента и подтверждения получения

## 1. Кратко: как всё устроено

Система строится вокруг трёх сущностей:

- Пользователь: [server/models/User.js](server/models/User.js)
- Трек: [server/models/Track.js](server/models/Track.js)
- Статус: [server/models/Status.js](server/models/Status.js)

Основная логика находится в:

- [server/routes/status.routes.js](server/routes/status.routes.js)
- [server/middleware/track.middleware.js](server/middleware/track.middleware.js)
- [server/routes/bookmark.routes.js](server/routes/bookmark.routes.js)
- [server/middleware/bookmarks.middleware.js](server/middleware/bookmarks.middleware.js)
- [client/src/components/MainBookmarks.jsx](client/src/components/MainBookmarks.jsx)
- [client/src/components/Parcels2.jsx](client/src/components/Parcels2.jsx)

Идея следующая:

- статус — это не просто текст, а часть истории доставки;
- у каждого пользователя есть свой контекст: филиал, роль, список закладок;
- клиентская часть получает не “сырой” статус, а вычисленный, роль-ориентированный набор статусов;
- подтверждение получения — это отдельный бизнес-экшен, который переносит посылку из активных закладок в архив.

## 2. Как появляется статус “Прибыло в филиал …”

Основная логика находится в [server/routes/status.routes.js](server/routes/status.routes.js).

### 2.1. Генерация динамического филиального статуса

Есть функция `ensureFilialArrivalStatus(filialName)`, которая делает следующее:

1. строит строку вида `Прибыло в филиал ${filialName}`;
2. ищет такой статус в коллекции `Status`;
3. если не находит — создаёт новый объект статуса;
4. возвращает объект статуса.

Это важно: status создаётся динамически, а не хранится жёстко как фиксированная запись для каждого филиала.

### 2.2. Куда берётся название филиала

Название филиала берётся из поля `selectedFilial` пользователя в [server/models/User.js](server/models/User.js).

Если роль пользователя — `client` или `filial`, сервер делает:

```js
if (currentUser && ['filial', 'client'].includes(currentUser.role)) {
  const ownFilialName = String(currentUser.selectedFilial || '').trim();
  if (ownFilialName) {
    userFilialStatus = await ensureFilialArrivalStatus(ownFilialName);
  }
}
```

То есть для клиента или филиала система понимает: “этот человек привязан к филиалу X, значит ему нужен статус “Прибыло в филиал X””.

### 2.3. Почему это нужно

Потому что филиал может быть разный:

- Астана
- Алматы
- Бишкек
- и т.д.

Если бы статус был жёстко зашит, это не масштабировалось бы. Поэтому используется динамический шаблон:

- `Прибыло в филиал ` + название филиала

## 3. Как сервер формирует список статусов для пользователя

Это основная роль [server/routes/status.routes.js](server/routes/status.routes.js).

### 3.1. Для клиента

Для `role === 'client'` сервер:

- берёт все статусы из базы;
- отбрасывает те, которые начинаются с `Прибыло в филиал `;
- оставляет статусы до “Получено” включительно;
- затем специально вставляет филиальный статус рядом с “Получено”.

Так клиент видит:

- ...
- статус до филиала
- “Прибыло в филиал <название>”
- “Получено”

Но при этом не видит все внутренние статусы, которые не относятся к клиентскому потоку.

### 3.2. Для филиала

Для `role === 'filial'` сервер формирует очень узкий набор:

- `userFilialStatus`
- `Получено`

То есть филиал часто работает только с двумя значимыми этапами:

1. товар прибыл в филиал;
2. товар получен.

### 3.3. Для admin / china

Для `admin` и `china` показывается полный список статусов, но без “Прибыло в филиал …”, потому что эта часть служит клиентскому/филиальному контексту, а не внутреннему админскому потоку.

## 4. Где в историю трека добавляются статусы

Основная логика находится в [server/middleware/track.middleware.js](server/middleware/track.middleware.js).

### 4.1. Функция `buildHistoryEntries`

Когда добавляется статус `Получено`, система не пишет только один элемент в историю. Она создаёт два:

```js
return [
  { status: arrivalStatus._id, date },
  { status: statusObj._id, date }
];
```

То есть в `track.history` реально будет:

- `Прибыло в филиал Астана`
- `Получено`

### 4.2. Почему это важно

Потому что история трека хранит событие, а не только “текущий флаг”.

Это даёт возможность:

- отследить цепочку шагов;
- показать историю клиенту;
- вычислять “актуальный” статус по правилам.

---

## 5. Как вычисляется “актуальный” статус для клиента

Основной код находится в [server/routes/track.routes.js](server/routes/track.routes.js), в функции `resolveTrackStatus`.

### 5.1. Логика вычисления

Если последняя запись истории = `Получено`, и перед ней есть статус вида `Прибыло в филиал ...`, то сервер возвращает именно предыдущий статус как “текущий”.

То есть фактически база может хранить:

```text
["Прибыло в филиал Астана", "Получено"]
```

Но клиентскому UI показывается:

```text
"Прибыло в филиал Астана"
```

Это сделано не случайно: бизнес-логика говорит, что “посылка уже в филиале”, и конечная часть “получено” считается фактом закрытия, но не всегда “текущий статус” в интерфейсе клиента.

### 5.2. Почему это не приводит к путанице

Потому что в системе есть различие между:

- `history` — полная последовательность событий;
- `currentStatus` / “актуальный статус” — вычисляемый, для UI;
- “Получено” — факт подтверждения приёмки.

Это технически правильная архитектура, когда одно и то же событие понимается по-разному в разных контекстах.

## 6. Где появляется статус “Готов к выдаче”

Это отдельный важный статус и он используется как триггер для клиента:

- [server/middleware/bookmarks.middleware.js](server/middleware/bookmarks.middleware.js)
- [client/src/components/Parcels2.jsx](client/src/components/Parcels2.jsx)
- [client/src/components/MainBookmarks.jsx](client/src/components/MainBookmarks.jsx)

### 6.1. Как рассчитывается `readyForPickup`

В [server/middleware/bookmarks.middleware.js](server/middleware/bookmarks.middleware.js) есть проверка:

```js
const readyForPickup = track.history.some(
  (h) => h.status && h.status.statusText === 'Готов к выдаче'
);
```

Если в истории трека есть такой статус, то для закладки ставится флаг:

```js
readyForPickup: true
```

### 6.2. Почему это важно

Потому что этот флаг используется на клиенте как сигнал:

-“эта посылка уже готова к выдаче”;
- кнопка подтверждения получения может быть показана;
- список посылок можно сортировать таким образом, чтобы готовые к выдаче были первыми.

### 6.3. Сортировка

В этом же файле порядок сортировки такой:

```js
updatedBookmarks.sort((a, b) => {
  if (a.readyForPickup !== b.readyForPickup) {
    return b.readyForPickup - a.readyForPickup;
  }
  return new Date(b.createdAt) - new Date(a.createdAt);
});
```

То есть готовые к выдаче посылки выводятся сначала.

## 7. Где клиент подтверждает получение товара

### 7.1. Клиентский вызов

На клиенте это видно в [client/src/components/Parcels2.jsx](client/src/components/Parcels2.jsx):

```js
const handleConfirmReceipt = async (trackNumber) => {
  const response = await axios.post(`${config.apiUrl}/api/bookmark/confirm-receipt`, {
    phone,
    trackNumber
  });
};
```

Если запрос успешен, клиент видит toast и удаляет посылку из активных закладок.

### 7.2. Серверный маршрут

В [server/routes/bookmark.routes.js](server/routes/bookmark.routes.js) есть маршрут:

```js
router.post('/confirm-receipt', async (req, res) => {...})
```

Логика работы:

1. Получает `phone` и `trackNumber` из body;
2. ищет пользователя по номеру телефона;
3. находит нужную закладку в `user.bookmarks`;
4. берёт `trackId` из закладки;
5. получает сам трек и его `history`;
6. создаёт архивный объект;
7. кладёт его в `user.archive`;
8. удаляет закладку из `user.bookmarks`;
9. сохраняет пользователя.

### 7.3. Что именно происходит после подтверждения

После подтверждения посылка считается принята:

- она больше не активна в закладках пользователя;
- она хранится в архиве;
- в архиве сохраняется история трека и дата получения;
- у пользователя появляется фактическое подтверждение получения товара.

### 7.4. Важное замечание

Эта операция не меняет статус трека на “Получено” через `Track.status`. Она скорее выполняет бизнес-операцию “клиент подтвердил получение” и переносит данные в архив.

То есть статус “Получено” может быть уже в истории трека, а подтверждение клиента — это отдельное действие, которое вносит посылку в архив и завершает её жизненный цикл в активном списке.

## 8. Где кнопка “Подтвердить получение” появляется

На клиенте кнопка показывается только когда:

- закладка имеет `readyForPickup === true`
- то есть в истории трека есть статус `Готов к выдаче`

Пример из [client/src/components/Parcels2.jsx](client/src/components/Parcels2.jsx):

```jsx
{bookmark.readyForPickup && (
  <button className='confirmTrack' onClick={() => handleConfirmReceipt(bookmark.trackNumber)}>
    Подтвердить получение
  </button>
)}
```

То есть эта кнопка — не “проверка статуса вообще”, а “сигнал, что товар уже готов к выдаче”.

---

## 9. Техническая цепочка “Готов к выдаче → подтверждение получения”

```text
Админ / филиал создаёт статус: "Готов к выдаче"
        ↓
Трек получает этот статус в history
        ↓
сервер вычисляет bookmark.readyForPickup = true
        ↓
клиент видит кнопку "Подтвердить получение"
        ↓
клиент отправляет POST /api/bookmark/confirm-receipt
        ↓
сервер находит пользователя и закладку
        ↓
сохраняет историю в user.archive
        ↓
удаляет закладку из active bookmarks
        ↓
посылка считается полученной
```

## 10. Главный вывод

### 10.1. Филиальный статус

Это “динамически созданный” статус типа:

- `Прибыло в филиал Астана`

Он генерируется из `selectedFilial` и нужен для контекста доставки.

### 10.2. Статус “Готов к выдаче”

Это триггер, который показывает, что товар уже можно выдавать клиенту.

### 10.3. Подтверждение получения

Это отдельный шаг, когда клиент подтверждает факт приёма:

- перенос в архив;
- удаление из активных треков;
- сохранение истории получения.

### 10.4. Важная архитектурная мысль

Система разделяет:

- логическую историю трека;
- состояние “готово к выдаче”;
- факт подтверждения клиентом;
- UI-представление на стороне клиента.

Именно поэтому в проекте одна и та же посылка может быть “готова к выдаче”, “в филиале”, “получена” и одновременно находиться в разном контексте в разные моменты.
